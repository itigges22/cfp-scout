# ADR-0008 — Matcher v2: enrichment + lexical co-signal + distinctiveness pillar + LLM-as-judge

**Status:** Accepted · 2026-05-26
**Supersedes:** ADR-0005 (Auto-run matcher on first view) — still in force but
the matcher it triggers is now the v2 pipeline described here.

## Context

The v1 matcher (ADR-0005 era) was a three-stage cosine pipeline:

1. **Stage A — Messaging fit:** top-K mean of cosine similarities
   between the conference's embedded text and the messaging chunks.
2. **Stage B — Pillar alignment:** for each strategic pillar, cosine
   between the conference and that pillar's description; take the
   **max** across pillars.
3. **Stage C — SME fit:** weighted blend of topic / audience / bio /
   location / past-attendance signals.

The output looked correct on synthetic test data but degenerated
badly on the real corpus:

- **Every conference scored ~100% on messaging fit** — the raw
  dot-product `_cosine_sim` wasn't normalizing magnitudes (the
  embeddings aren't unit vectors; ‖v‖ ≈ 13–18 for the model in
  use). The old code was effectively comparing dot products
  directly. Once the bug was fixed, the issue inverted: messaging
  scored ~0 for nearly everything because nomic-embed-text-v1-5
  produces a narrow cosine band (corpus p95 ≈ 0.05) for short-form
  vs long-form text.
- **Every conference scored 100% on pillar alignment** — taking the
  max across 4 pillar cosines saturates whenever at least one
  pillar clears the rescale ceiling, which is "always" for any
  AI-adjacent event.
- **Bare conference text is ~14 words** — name + topics + location.
  The embedder has nothing to compare against the operator's
  ~200-word messaging documents.

The combined effect was a dashboard where every conference scored
~95% and the matcher provided zero ranking signal.

## Decision

Rebuild the matcher around five coordinated changes — three input
fixes + two new pipeline stages.

### 1. LLM enrichment of conference text

Every conference's bare name+topics blob is LLM-expanded into a 2-3
sentence factual description with concrete technical vocabulary
(vLLM, MLOps, RAG, Kubernetes, …). The matcher's embedder reads
this enriched text instead of the 14-word bare blob.

- Stored on `app.conferences.enriched_description` (TEXT nullable).
- Generated by `app.services.enrichment.enrich_conference` —
  temperature 0.2, ~70 words median output, ~$0.0002 per call.
- Triggered automatically by `enrich_and_match_task` on every new
  ingest (both the developers.events feed and the LLM-extraction
  upload path).
- Bulk backfill via `scripts/enrich_and_reembed.py`.

### 2. LLM enrichment of pillar text

Same trick applied to the strategic pillars: each of the (4-ish)
pillars gets a 500-800 word long-form description LLM-extracted
from the operator's messaging documents. The matcher's Stage B
embeds this rich text instead of the operator's short
operator-authored tagline.

- Stored on `app.strategic_pillars.enriched_description` (TEXT
  nullable).
- Generated by `app.services.pillar_enrichment.enrich_pillar` —
  takes all active messaging documents as context and asks the
  LLM to extract everything related to ONE specific pillar.
- One-shot script: `scripts/enrich_pillars.py`.

### 3. Lexical co-signal in Stage A

The messaging-fit score is now a 55/45 blend of:

- **Embedding score** — top-K mean cosine, rescaled against an
  empirical floor/ceiling.
- **Lexical score** — keyword-overlap score against the
  auto-extracted vocabulary of the active messaging chunks, with
  hand-curated weights on a small vendor-neutral list of high-value
  technical terms (vLLM, MLOps, RAG, …). Capped saturation so
  generic word-soup can't max it out.

This is the **hybrid retrieval** pattern from the 2026 RAG
literature — see references below. Lexical signal compensates for
the narrow cosine band of the embedding model on short vs long
text. Without it, well-named events like "vLLM Meetup London" score
0% on messaging despite being an obvious match.

### 4. Distinctiveness-weighted pillar aggregation

Stage B no longer takes `max(rescaled_per_pillar_score)`. Instead:

```
peakedness = softmax_t(per_pillar_raw_cosines)
composite = top_raw_cosine × (0.4 + 0.6 × normalized_peakedness)
score     = rescale(composite, floor=0.10, ceiling=0.40)
```

with softmax temperature t=50 so the 0.05-typical cosine
differences across pillars get amplified into a meaningful
peakedness signal. The result:

- A conference cleanly peaked on ONE pillar (e.g. an agentic-named
  event with high cosine to "Agentic AI innovation" and low to the
  other 3) → composite ≈ top, score → 1.0.
- A conference uniformly relevant to all 4 pillars (generic AI
  adjacency, e.g. "AI Conference 2026") → composite ≈ 0.4 × top,
  score → 0.4-0.5.
- Off-topic events → all cosines low, composite low, score → 0.

This breaks the "everyone at 100% on pillar" saturation while
still giving generic AI events a non-zero baseline.

### 5. Stage D — LLM-as-judge cross-encoder

After stages A/B/C, the matcher makes one extra LLM call asking
llama-scout-17b to score the conference against the full pillar
context on a calibrated 0..100 scale, with a one-sentence rationale.

This is the **cross-encoder reranker** pattern from the RAG /
dense-retrieval literature — except we use the chat LLM as the
cross-encoder via structured prompting (the operator's MaaS key
doesn't expose a dedicated reranker model). Same idea: the model
sees both query + document together and produces a single
relevance score.

- New columns: `app.matches.judge_score` (REAL nullable) +
  `judge_rationale` (TEXT).
- Service: `app.services.matcher.judge.judge_conference`.
- Operator-tunable: `settings.enable_llm_judge` (default True) +
  `settings.match_w_judge` (default 0.30).
- When the judge is disabled or fails, `overall_score` re-normalizes
  across A/B/C only — no stage is ever silently zeroed.

## Consequences

**Calibration data after rollout** (576-conference corpus, 5 active
messaging docs, 4 strategic pillars):

| Score | Distribution | Sample top picks |
|-------|-------------|------------------|
| Overall | 1 @ 60%, 31 @ 50%, 67 @ 40%, 174 @ 30%, 244 @ 20%, 65 @ 10% | Conf42 LLMs (65), AgentCamp Auckland (54), vLLM Istanbul (52), KubeCon EU 2028 (50) |
| Pillar  | Spread 0–100%, no saturation. 36 conferences hit 100% (truly pillar-peaked) | Agentic-named events; vLLM events at 60–78% |
| Judge   | Calibrated by prompt: 0–29 off-topic, 30–49 tangential, 50–69 broad AI, 70–89 strong fit, 90–100 perfect | vLLM Meetup London: 0.90 · PyTorch 2027: 0.50 · Devoxx Morocco: 0.00 |

**Cost** of running the v2 matcher end-to-end on the full corpus
(~576 conferences):

- Enrichment (conferences): ~$0.30 one-time.
- Enrichment (pillars): ~$0.02 one-time per pillar set.
- Bulk judge: ~$0.30 per full rescore.
- Per-ingest: 1 LLM enrichment + 1 LLM judge ≈ $0.001 per new conference.

**Operator knobs** for cost control:

- `settings.enable_llm_judge` — turn off Stage D entirely.
- `settings.match_w_judge` — weight the judge less if budget is
  tight; remaining stages auto-renormalize.
- `settings.llm_max_concurrent_calls` — caps concurrent LLM calls
  across the whole process.

## Negative space

- We did NOT switch from custom lexical to proper BM25 (e.g.
  `rank_bm25` package). The custom scorer is fine for a 5-doc
  corpus; BM25 would be the right next step if the messaging
  corpus grows past ~50 documents.
- We did NOT add a dedicated cross-encoder reranker model
  (BGE-Reranker-v2-m3, Jina Reranker v2, etc.) because the
  operator's MaaS key only exposes the chat model. If a dedicated
  reranker becomes available, swap it into the judge service —
  the interface (one float + a rationale string per conference)
  is unchanged.
- We did NOT implement Reciprocal Rank Fusion for combining lexical
  + dense rankings. The current 55/45 blend works for this corpus
  size; RRF would be a clean follow-up if either signal's scale
  changes.
