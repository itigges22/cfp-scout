# Database migrations

Scout uses Alembic for schema migrations. This runbook covers the
day-to-day operations. Design rationale lives in [ADR-0004](../ADR/0004-async-sqlalchemy-and-alembic.md).

## Daily commands

```bash
make migrate                          # alembic upgrade head
make migrate-create MSG="add foo"     # generate a new revision via autogenerate
make migrate-current                  # show currently-applied revision
make migrate-history                  # full revision history
```

Each runs inside the api container — `docker compose exec -T api alembic ...` under the hood. You don't need Python or Alembic on the host.

## How it works

- **Migration scripts** live in `apps/api/alembic/versions/`.
- **Naming**: `YYYYMMDD_HHMM_<slug>.py` (set by `file_template` in `alembic.ini`). Sortable, human-readable, no ambiguous hash-only filenames.
- **Connection**: Alembic uses the **Postgres superuser** (`POSTGRES_USER` from `.env`), not the runtime `app` role. DDL needs superuser privileges; see [ADR-0002](../ADR/0002-postgres-schemas-not-databases.md) for the role rationale.
- **Async**: `alembic/env.py` uses `async_engine_from_config` + `connection.run_sync(...)` so Alembic plays nice with our async stack. You don't think about this; just run `make migrate`.

## Workflow: change a model

1. Edit the model in `apps/api/app/db/models/...`.
2. Generate a revision:

   ```bash
   make migrate-create MSG="add chunk_metadata to document_chunks"
   ```

3. Open the generated file in `apps/api/alembic/versions/`. **Always read the autogenerated SQL** — Alembic doesn't catch everything (e.g. data migrations, custom indexes, type changes that need USING clauses). Edit if needed.
4. Test:

   ```bash
   make migrate                  # apply
   make migrate-current          # confirm
   # ... run any smoke tests ...
   ```

5. To roll back during local testing:

   ```bash
   docker compose exec -T api alembic downgrade -1
   ```

6. Commit the revision file along with the model change. Migration filename goes in the commit message.

## Common gotchas

### "Target database is not up to date"
You changed a model and ran `make migrate-create` but didn't apply prior pending migrations first. Run `make migrate` first, then regenerate.

### Autogenerate produced an empty `upgrade()` / `downgrade()`
Either your model change isn't reaching `Base.metadata` (check `app/db/models/__init__.py` exports the new module) or the change is invisible to autogenerate (custom server defaults, `comment=...` changes, etc.). Hand-write the migration in that case.

### "permission denied for schema app" after a migration
The new table didn't pick up the default privileges granted in `02-roles-and-schemas.sql`. This shouldn't happen if you created the table via Alembic in one of our four schemas, but if it does, the migration needs an explicit GRANT:

```python
op.execute("GRANT SELECT, INSERT, UPDATE, DELETE ON app.new_table TO app;")
```

### Migration applies in dev but fails in fresh install
Common cause: the migration assumed an extension or role already existed. Both are in `infra/postgres/init/*.sql` which runs *before* Alembic, so fresh installs should work. If they don't, add the dependency to the init SQL with a guard (`IF NOT EXISTS`).

### Downgrading a migration that drops a column
`op.drop_column()` is irreversible — the data is gone unless your downgrade has a `bulk_insert` with backed-up data. For destructive changes:
1. Take a backup first: `make db-dump`
2. Apply the change
3. If you need to roll back, restore: `make db-restore FILE=...`

## Schema layout in migrations

Every model declares its schema via `__table_args__`:

```python
class MessagingDocument(Base):
    __tablename__ = "messaging_documents"
    __table_args__ = {"schema": "app"}
```

When generating migrations, Alembic respects this — tables land in the
right schema. Junction tables go in `app`, document_chunks in `vectors`,
audit_log + content_versions in `audit`, the APScheduler jobstore in `jobs`.
