# 33 — Conference Brief Export (One-Pager)

## Goal
When the team approves a conference, generate a **one-page brief** with
everything an attendee or manager needs to act. The brief is what they
actually paste into Slack, send to their VP, or print before they fly.

HTML-based (printable to PDF via browser print). No server-side PDF rendering
in Phase 1 — keeps the api image lean.

## Prereqs
- 17 (matcher + rationale)
- 19 (SME fit narratives)
- 20 (conference detail page)
- 23 (conference series — past attendance summary)
- 32 (team recommendations — recommended team)
- Active messaging documents from step 09 (talking points)

## What's in the brief

Single-column, print-optimized layout. Sections, in order:

1. **Header**
   - Conference name (large), dates, location
   - Conference website link
   - "Generated by Scout on YYYY-MM-DD" footer text

2. **At a glance**
   - Overall fit score (0–100 + bucket badge)
   - Three small score bars: Messaging / Pillar / SME
   - Series membership: "Edition N of [Series]; DAAM has attended X of past 5"
   - Acceptance rate if known
   - Estimated cost (registration)

3. **Why we're going**
   - Rationale text from step 17 (the AI-generated paragraph)
   - Top pillar tag(s) the conference aligns with
   - Top 3 conference topics that match our messaging

4. **Recommended attendee(s)**
   - Pulls from step 32's team recs
   - Defaults to **team-of-1** (most common case)
   - Switchable to team-of-2 or team-of-3 via a query param (`?team_size=2`)
   - For each recommended SME: name, location, fit narrative from step 19,
     topic coverage chips
   - When team_size > 1: short templated rationale ("Sarah covers RAG, Marcus
     covers MLOps — together they cover 5 of 6 topics")

5. **CFP information**
   - Each `cfp_deadlines` entry as a row: kind, date, days remaining,
     description
   - Bold the next upcoming deadline
   - `cfp_topics_of_interest` list (top 10)
   - Link to the CFP page

6. **Past DAAM engagement** (from `past_conferences` + series)
   - For each past edition in the series: year, attendees, notes
   - Empty state: "No prior DAAM attendance recorded for this series."

7. **Talking points** (pulled from active messaging documents)
   - Top 3 messaging documents whose chunks scored highest against this conference
   - For each: title + the top 2 `talking_points` entries (from structured
     messaging fields in step 05)
   - These are what the SME paraphrases on stage / at the booth

8. **Logistics placeholder**
   - Template section for the team to fill in once approved: travel, lodging,
     swag/booth, sponsorship status
   - Rendered as a `<div contenteditable>` so the user can type into the
     page before printing — saved to `localStorage` per-conference

9. **Footer**
   - URL to the conference detail page in Scout
   - Generation timestamp + Scout version

## Implementation

### Backend
- [ ] `GET /api/v1/conferences/{id}/brief` returns a denormalized JSON
      payload with all the sections above (one request, no waterfall).
- [ ] Service `app/services/brief/builder.py` assembles the payload from:
  - `conferences`, `matches`, `match_team_recommendations`, `decisions`
  - `conference_series` (history via `past_conferences.series_id`)
  - Top messaging documents via `similar_chunks` for the conference text
- [ ] Cached 5 minutes in the api process (changes mid-day shouldn't
      regenerate from scratch on every print).

### Frontend
- [ ] `/conferences/[id]/brief` is its own route in the SPA — full-page
      layout, **no left rail, no top bar**, print-optimized.
- [ ] Tailwind print styles:
  - A4 page size, 0.5in margins
  - `@media print` rules hide nav, hide buttons, force page-break sensible places
  - Black text on white background; print-safe colors for score bars
- [ ] **Export actions** in the top-right of the on-screen view (hidden in print):
  - **Print** button → triggers `window.print()`
  - **Copy as Markdown** button → assembles a markdown version, copies to clipboard
    (useful for Slack)
  - **Copy as HTML** button → for email
- [ ] `?team_size=1|2|3` query param switches the recommended-attendee section.
- [ ] Logistics section uses `contenteditable` with `localStorage` persistence
      keyed by conference id.

### Dashboard integration (step 20)
- [ ] Conference detail page gets a **"Generate Brief"** button (visible when
      `status='approved'` or admin override).
- [ ] Opens the brief in a new tab.
- [ ] Approve action prompts: "Generate brief now?" (optional convenience).

## Cost
- Zero LLM calls — purely composing data we already have.
- Backend is one assembling query (cached 5min). UI is a static-ish render.

## Security notes
- The brief surfaces messaging-document talking points. **For locally-stored
  RH-internal data**, this is fine since the user explicitly clicks "Generate Brief"
  and prints it themselves.
- The `contenteditable` logistics block stores only in `localStorage`; never
  posted to the server.
- Copy-to-clipboard runs client-side; no external posting.
- Print stylesheet excludes the "AI-generated" badges by default (the brief
  reads as a team artifact, not as a chatbot output) — but the rationale text
  itself is unchanged and still attributable. Document this in step 30.

## Acceptance criteria
- [ ] `/conferences/[id]/brief` renders all 9 sections for an approved conference
      with full data.
- [ ] Empty states for each section gracefully degrade (no past attendance →
      "No prior engagement"; no team rec → fall back to top SME individual).
- [ ] `?team_size=2` swaps the attendee section to the team-of-2.
- [ ] Browser `Cmd-P` produces a clean one-page PDF (or two pages max).
- [ ] "Copy as Markdown" produces output that pastes readably into Slack.
- [ ] Logistics edits persist across page reloads via localStorage.

## Open questions for the user
- **WeasyPrint server-side PDF generation?** Heavier dep (Cairo + Pango,
  ~150MB), but enables true server-rendered PDFs and email attachments.
  Recommend NO for Phase 1; browser print-to-PDF is fine. Confirm.
- **Email the brief from Scout?** Recommend NO (avoids SMTP setup). Users
  paste from Markdown into their own email tools.
- **Default team_size for the brief** — 1 (most common). Switchable.

## Risks
- Print rendering varies by browser. Test in Chrome, Firefox, Safari.
- Long talking points or many deadlines can push to 2 pages. Truncation
  rules (top 3 messaging docs, top 10 topics, max 5 past editions) keep
  it usually-one-page.
